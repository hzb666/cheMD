## `:::procedure` Blocks

`:::procedure` produces a `ProcedureNode`. The block header ID becomes the procedure ID. Top-level fields are `ref`, `reaction`, and `evidence`. Prose is stored in `body`, explicit steps are stored in `steps`, and nested Markdown or structured content is stored in `children`.

```md
:::procedure #proc-main
reaction: @rxn-main
evidence: labnote-page-12

step: charge | id=s-charge | inputs=@mol-aryl,@mol-boron | outputs=mixture-a
step: heat | id=s-heat | temperature=90 C | duration=12 h | dependsOn=s-charge
step: analyze | id=s-tlc | analysisType=tlc | dependsOn=s-heat
:::
```

The compiler option `procedureMode` controls semantic conversion. `auto` uses explicit steps when present and lowers prose otherwise; `explicit` requires explicit steps; `lowered` always lowers prose.

## Inline `step:` Syntax

Inline steps use `step: family | key=value`. The first non-parameter segment becomes `family`. `id` or `step_id` sets `stepId`. Structural keys are `id`, `step_id`, `family`, `inputs`, `outputs`, `depends_on`, `dependsOn`, `stage`, `purpose`, `evidence`, and `confidence`.

Non-structural keys enter `params`, where the typechecker performs quantity parsing, reference resolution, and family-specific validation. `inputs`, `outputs`, `dependsOn`, and `evidence` use comma-separated values. `confidence` is stored only when it parses to a finite number.

## Nested `:::step` Syntax

Procedures support nested `:::step` blocks. Header `#id` can provide the step ID, and the `family` field is required. Nested steps use the same structural keys as inline steps; ordinary fields enter `params`.

```md
:::procedure #proc-workup
reaction: @rxn-main

:::step #s-quench
family: quench
stage: workup
reagent: NH4Cl(aq)
temperature: 0 C
:::
:::
```

Explicit steps carry provenance: source node type `procedure`, source type `explicit_step`, and raw text from the original step line or block fields.

## Step `inputs`, `outputs`, and `dependsOn`

`inputs` and `outputs` are resolved by `step-references`. When an object index exists, local objects and external targets can resolve to typed references; unresolved bare values are retained as raw values. `dependsOn` must target an existing step ID and participates in cycle detection.

Explicit step families:

`charge`, `add`, `transfer`, `mix`, `cool`, `heat`, `hold`, `purge`, `quench`, `extract`, `wash`, `separate_layers`, `filter`, `dry`, `concentrate`, `purify`, `sample`, `analyze`, `observe`, and `store`.

Parameter validation:

| family | rule |
| --- | --- |
| `heat` | requires `temperature`, `target_temperature`, or `duration` |
| `cool` | requires `temperature`, `target_temperature`, or `method` |
| `analyze` | requires `analysisType`, `analysis_type`, or `type` |
| `extract` | requires `solvent` |
| `filter` | allows only `medium` and `wash` |
| `purge` | defaults missing `atmosphere` to `nitrogen` |

## `evidence` and `confidence`

Procedure-level `evidence` records evidence for the procedure block. Step-level `evidence` is stored as a string array and feeds evidence edges in the step graph. `confidence` stores user-provided confidence for explicit steps; the typechecker defaults explicit steps to 1 when it is absent.

Quantity-like step parameters use the shared quantity parser: `amount`, `mass`, `volume`, `temperature`, `target_temperature`, `duration`, `time`, `pressure`, `concentration`, `equivalent`, `equivalents`, `percent`, `rate`, `rpm`, and `ph`.

## Procedure Control Flow

Control flow is written inside `:::procedure` with the same line-oriented style as `step:`. Use braces for nested control bodies. `repeat` is statically expanded into concrete steps, while `until`, `branch`, `wait`, and `abort_if` stay as dynamic controls in the control graph. `parallel` statically records each path and is checked by runtime preflight for resource conflicts.

```md
:::procedure #proc-controlled
reaction: @rxn-main

step: charge | id=s-charge | inputs=@mat-substrate | outputs=mixture-a

repeat: wash-cycle | count=2 {
  step: wash | solvent=brine | volume=10 mL
}

until: monitor-tlc | condition=@ana-tlc.result == complete | max_iterations=4 {
  step: analyze | id=s-tlc-check | type=tlc
}

branch: ph-workup {
  case: acidic | condition=sensor.ph < 7 {
    step: add | reagent=NaHCO3(aq) | rate=0.5 mL/min
  }
  default: neutral {
    step: hold | duration=0 min | note=skip neutralization
  }
}

parallel: workup {
  path: organic {
    step: dry | medium=Na2SO4
  }
  path: aqueous {
    step: store | location=waste
  }
}

wait: operator-approval | condition=operator.confirmed | timeout=30 min
abort_if: unsafe-temperature | condition=sensor.temperature > 80 C
:::
```

Control conditions should be machine-checkable. References such as `@ana-tlc` must resolve, and bare prose conditions are errors because the runtime cannot decide them reliably.

## `:::observation` Blocks

`:::observation` produces an `ObservationNode`. The current top-level field is `ref`. Prose is stored in `body`, explicit events are stored in `events`, and nested Markdown or structured content is stored in `children`.

```md
:::observation #obs-main
ref: @proc-main
event: color_change | id=e-color | value=yellow | linkedStep=s-heat | confidence=0.8
event: gas_evolution | id=e-gas | severity=moderate | linked_step=s-quench
:::
```

## Inline `event:` Syntax

Events use `event: event_type | key=value`. Structural keys are `id`, `event_id`, `type`, `eventType`, `event_type`, `stage`, `timepoint`, `severity`, `linked_step`, `linkedStep`, `evidence`, and `confidence`. Non-structural keys enter `params`.

Implemented explicit event types:

| event type | purpose |
| --- | --- |
| `color_change` | color change |
| `precipitation` | precipitate formation |
| `gas_evolution` | gas formation |
| `phase_change` | phase change |

`value`, `color`, or `state` is written as the normalized value. Unknown event types produce `E_OBSERVATION_EVENT_INVALID_TYPE`.

## Event and Step Links

Events write `linkedStepId` through `linkedStep` or `linked_step`. The typechecker validates links after all procedure steps are resolved. Missing targets produce `E_OBSERVATION_LINKED_STEP_MISSING`. The public step graph stores observation records and diagnostics; export/training layers can materialize an `event_observed_step` relation from validated event links.

Prose lowering is implemented by `@chemd/step-ontology`. Procedure lowering detects sentence patterns for charge, purge, cool, heat, quench, add, hold, extract, dry, concentrate, separate_layers, filter, sample, analyze, and observe. Observation lowering detects color change, precipitation, and gas evolution. Lowering emits warnings to identify semantics inferred from prose.

## Runtime Trace

Use `:::trace` when a run, replay, or imported device log needs to record what actually happened. Trace events point at the procedure plan, step IDs, and control IDs; they do not rewrite the procedure or result.

```md
:::trace #run-main
plan: @proc-controlled
mode: human-run
event: run_started | at=2026-05-20T09:00:00Z
event: step_started | step=s-charge | at=2026-05-20T09:01:00Z
event: control_entered | control=operator-approval | at=2026-05-20T09:04:00Z
event: control_completed | control=operator-approval | at=2026-05-20T09:05:00Z
event: deviation_recorded | step=s-tlc-check | field=iteration_count | expected=1 | actual=3
event: run_completed | at=2026-05-20T09:40:00Z
:::
```

## Best Practice Example

Use explicit steps and events when graph export, runtime preflight, or evidence export needs stable structure. Keep prose for narrative context.

```md
:::procedure #proc-main
reaction: @rxn-main
evidence: notebook-p12
step: charge | id=s-charge | inputs=@mol-substrate | outputs=mixture-a
step: heat | id=s-heat | temperature=60 C | duration=3 h | dependsOn=s-charge
step: analyze | id=s-tlc | analysisType=tlc | dependsOn=s-heat
:::

:::observation #obs-main
ref: @rxn-main
event: color_change | id=e-color | stage=reaction | linkedStep=s-heat | color=yellow | evidence=photo-1
event: gas_evolution | id=e-gas | severity=low | linkedStep=s-charge
Mixture became yellow during heating.
:::
```
