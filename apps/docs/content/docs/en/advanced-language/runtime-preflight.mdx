---
title: Runtime Preflight
description: How Chemd runtime-lab turns compiled steps and controls into run plans, preflight issues, and manual or adapter gates.
---

The runtime layer does not change Chemd syntax. It consumes the canonical step graph and control graph produced by the language pipeline and prepares a run plan for dry runs, human runs, robot runs, or replay.

## Runtime Inputs

Runtime preflight starts from procedure steps. Keep step IDs stable when later observations, artifacts, or external run records need to point back to the same operation.

```mdx
:::procedure #proc-runtime
step: cool | id=s-cool | target_temperature=-78 C
step: add | id=s-add | dependsOn=s-cool | reagent=n-BuLi
wait: operator-approval | condition=operator.confirmed | timeout=30 min
step: analyze | id=s-tlc | type=tlc | dependsOn=s-add
:::
```

## Run Plans

`@chemd/runtime-lab` exposes `buildRunPlan`. The plan ID is derived from the document ID and has the form `runplan::<documentId>`.

```ts
import { buildRunPlan, preflightRun } from "@chemd/runtime-lab";

const plan = buildRunPlan({
  documentId: "exp-runtime",
  stepGraph
});

const preflight = preflightRun(plan, {
  mode: "human-run",
  capabilities: ["cooling", "analytical_tlc"],
  adapters: [{ adapterId: "manual", supports: ["wait"], available: true }]
});
```

`preflight.blocking` becomes `true` when an error-level runtime diagnostic is emitted.

The run plan carries `steps`, `controls`, `controlStates`, and runtime diagnostics. Dynamic controls such as `wait`, `until`, `branch`, and `abort_if` start as `waiting_adapter` in `controlStates` because their next action depends on runtime state or operator input.

## Modes

The runtime mode is one of:

- `dry-run`: plan and inspect execution without controlling a lab run.
- `human-run`: keep manual execution in view and surface confirmation points.
- `robot-run`: require every step family to be known to the runtime planner.
- `replay-run`: replay a recorded run state or trace.

## Capabilities

Several step families imply capability requirements:

| Step family | Capability |
| --- | --- |
| `cool` | `cooling` |
| `heat` | `heating` |
| `purge` | `inert_gas` |
| `filter` | `filtration` |
| `purify` | `chromatography` |
| `dry`, `concentrate` | `vacuum` |
| `analyze` with `type=tlc` | `analytical_tlc` |
| `analyze` with `type=nmr` | `nmr` |
| `analyze` with `type=hplc` | `hplc` |

Missing capabilities produce runtime preflight diagnostics.

Capabilities, confirmation strategy, and safety tags are derived from the StepFamily schema in `@chemd/step-ontology`. Runtime packages should not duplicate a separate family map.

## CLI Preflight

User-facing runtime checks go through the CLI:

```text
chemd preflight experiment.chemd --mode human-run --format text
chemd preflight experiment.chemd --mode robot-run --context lab.json --format json --dry-run
```

`--mode` accepts `dry-run`, `human-run`, `robot-run`, and `replay-run`. `--format` accepts `text` and `json`. `--dry-run` marks the report as non-executing metadata; it does not weaken diagnostics.

The JSON report schema is `chemd-preflight/v0.1` and contains:

```json
{
  "schemaVersion": "chemd-preflight/v0.1",
  "dryRun": true,
  "filePath": "experiment.chemd",
  "mode": "robot-run",
  "preflight": {
    "blocking": true,
    "issues": [],
    "diagnostics": []
  }
}
```

## Context File

`--context lab.json` supplies lab state. The file is merged over default capabilities and can include adapters, devices, inventory, environment, and safety rules.

```json
{
  "capabilities": ["heating", "cooling", "analytical_tlc"],
  "devices": [
    { "capability": "heating", "min": 20, "max": 120, "unit": "C" }
  ],
  "inventory": {
    "materials": [
      { "id": "mat-substrate", "available": true, "hazards": ["acid"] },
      { "id": "mat-base", "available": false }
    ]
  },
  "adapters": [
    { "adapterId": "operator", "supports": ["wait", "abort_if"], "available": true }
  ],
  "safetyRules": [
    {
      "ruleId": "confirm-quench",
      "trigger": { "stepFamily": "quench" },
      "severity": "error",
      "requiresConfirmation": true,
      "message": "Quench requires operator confirmation."
    },
    {
      "ruleId": "acid-review",
      "trigger": { "materialHazard": "acid" },
      "severity": "warning",
      "requiresConfirmation": true,
      "message": "Acid handling requires review."
    },
    {
      "ruleId": "branch-review",
      "trigger": { "controlKind": "branch" },
      "severity": "warning",
      "message": "Branch controls require operator review."
    }
  ]
}
```

Safety rules can trigger on `stepFamily`, `param`, `materialHazard`, or `controlKind`. Material hazard rules use IDs from `inputs` or `materials` and match them against `inventory.materials[].hazards`.

## Preflight Issues

Runtime preflight emits both human-readable `issues` and compiler-shaped `diagnostics`.

| issue kind | diagnostic | meaning |
| --- | --- | --- |
| `capability` | `E605` | required capability is missing |
| `device_range` | `E_RUNTIME_DEVICE_RANGE` | temperature, pressure, rpm, or rate exceeds device bounds |
| `inventory` | `E_RUNTIME_INVENTORY` | required input material is unavailable or expired |
| `adapter` | `E_RUNTIME_ADAPTER` | robot-run lacks an adapter for a runtime action |
| `control` | `E_RUNTIME_CONTROL` | dynamic control requires runtime decision |
| `resource_conflict` | `E_RUNTIME_RESOURCE_CONFLICT` | `parallel` requires resource conflict review |
| `safety` | `W_RUNTIME_SAFETY` | safety rule or safety tag requires attention |

Error-level issues make `preflight.blocking` true and return CLI exit code 1. Warning-only issues keep exit code 0 but remain visible in the report.

## Confirmation Strategy

The runtime planner selects one confirmation strategy per step:

- `manual_required`: explicit high-touch actions such as `add`, `quench`, `purge`, `heat`, and `cool`.
- `review_inferred`: lowered steps or steps with low lowering confidence.
- `none`: steps that can proceed without a runtime confirmation gate.

This strategy is runtime metadata. It does not change parser, resolver, or typechecker behavior.

## Best Practice Example

Runtime-ready procedure records use explicit step IDs, dependency links, and step families that the runtime planner recognizes.

```md
:::procedure #proc-runtime-ready
reaction: rxn-main
step: charge | id=s-charge | inputs=@mol-substrate | outputs=mixture-a
step: cool | id=s-cool | target_temperature=-78 C | dependsOn=s-charge
step: add | id=s-add | reagent=n-BuLi | dependsOn=s-cool
wait: operator-approval | condition=operator.confirmed | timeout=15 min
step: analyze | id=s-tlc | type=tlc | dependsOn=s-add
:::
```

For `human-run`, this source produces manual confirmation points for high-touch operations and capability checks for cooling and TLC analysis.
