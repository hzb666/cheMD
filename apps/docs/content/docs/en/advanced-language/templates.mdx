## `:::template`

A template node contains `name`, `params`, `paramSpecs`, `bind`, optional `description`, and `body`. The template remains in document children, and `:::use` expands the template body during resolver execution.

```md
:::template reaction-note
params: rxn: ref<reaction> | label: string
description: reusable reaction note

Reaction `@param.label` records @param.rxn.
:::

:::use reaction-note
rxn: rxn-main
label: main oxidation
:::
```

Templates are useful for repeated explanatory text, procedure fragments, and analysis fragments. Template bodies can contain Markdown, structured blocks, and nested `:::use` calls.

Template headers support:

| Field | Meaning |
| --- | --- |
| `description` | Optional template description |
| `params` | Parameter declarations, using inline `|` lists or YAML-style lists |
| `bind` | Alias defaults, using `alias=source` pairs |

## `params`

`params` is a list field. YAML-style list items are also collected and converted into list values.

```md
:::template sample-row
params:
  - sample: ref<sample>
  - label: string
  - purity: quantity<percent>

Sample @param.label is @param.sample with purity @param.purity.
:::
```

Each list item uses `name: type`. A list item without a colon declares only the parameter name and is treated as `string`.

## String Parameters

Missing type declarations and `string` declarations produce `{ kind: "string" }`. The resolver checks that the parameter exists and is non-empty.

```md
:::template condition-line
params: label: string | note

Condition @param.label: @param.note
:::

:::use condition-line
label: entry 1
note: base changed from K2CO3 to Cs2CO3
:::
```

`note` has no explicit type and is equivalent to `note: string`. Missing or empty values produce template-parameter diagnostics.

## `ref<kind>` Parameters

Supported reference targets are `molecule`, `reaction`, `result`, `analysis`, `procedure`, `observation`, `sample`, `artifact`, and `condition_varies`. Type mismatches produce `E_TEMPLATE_PARAM_TYPE_MISMATCH`.

```md
:::template result-summary
params: result: ref<result> | sample: ref<sample>

Result @param.result was characterized by sample @param.sample.
:::

:::use result-summary
result: @res-main
sample: sample-main
:::
```

`ref<result>` only accepts result targets. Molecule, reaction, and missing targets are preserved in source and reported as diagnostics.

## `quantity<class>` Parameters

Quantity parameters validate a number followed by a unit. Supported classes include `amount`, `mass`, `volume`, `temperature`, `time`, `pressure`, `concentration`, `equivalent`, and `percent`.

```md
:::template heat-step
params: target: quantity<temperature> | duration: quantity<time>

:::procedure #proc-heating
step: heat to @param.target for @param.duration
:::
:::

:::use heat-step
target: 80 C
duration: 3 h
:::
```

Quantity parameters are type-checked during resolver execution. `80 C` is valid for temperature and `3 h` is valid for time; `80 C` is not valid for `quantity<mass>`.

## `bind`

`bind` uses `alias=source | alias2=source2`. The resolver checks use-node overrides first, template bindings second, and primary aliases last.

```md
---
id: bind-example
title: Bind example
date: 2026-05-19
primary_reaction: rxn-main
---

:::template bound-reaction-note
bind: reaction=rxn-template-default

Template body resolves @reaction.field through bind unless use overrides it.
:::

:::use bound-reaction-note
reaction: @rxn-main
:::
```

`bind` provides default aliases for a template. A same-named field on `:::use` has higher priority and can override the template default.

## `:::use`

`:::use template-name` stores all fields in `values`. List field values are joined with ` | `.

```md
:::template artifact-list
params: sample: ref<sample> | files: string

Sample @param.sample has artifacts: @param.files
:::

:::use artifact-list
sample: sample-main
files:
  - art-nmr-1h
  - art-hplc-report
:::
```

`files` is joined as `art-nmr-1h | art-hplc-report`. For structured evidence relations, keep artifact IDs in the `:::sample` `artifacts` field as well.

The resolver validates declared parameters before expansion:

- Missing required parameters produce `E_TEMPLATE_PARAM_MISSING`.
- `ref<kind>` parameters check local object existence and object type.
- `quantity<class>` parameters check quantity shape and units.

## Template Expansion Limits

The resolver caps template expansion depth at 32 and expanded nodes at 2000. Exceeding either limit produces `E_TEMPLATE_EXPANSION_LIMIT`.

```md
:::template many-nodes
params: label: string

:::result #res-@param.label
status: success
:::
:::

:::use many-nodes
label: run-001
:::
```

Expanded nodes still go through object indexing and required-field validation. The node-count limit protects a single source file from generating an excessive AST.

## Cycle Diagnostics

The resolver maintains a template stack. Re-entering a template already present in the stack produces `E_TEMPLATE_CYCLE`.

```md
:::template a
:::use b
:::
:::

:::template b
:::use a
:::
:::

:::use a
:::
```

This call chain forms `a -> b -> a`. The resolver stops cyclic expansion, emits `E_TEMPLATE_CYCLE`, and preserves the rest of the resolvable content.

## Parameter Types and Units

The `ref<kind>` kind set is molecule, reaction, result, analysis, procedure, observation, sample, artifact, and condition_varies. Parameter values must resolve to references with the expected target kind.

The `quantity<class>` class set is amount, mass, volume, temperature, time, pressure, concentration, equivalent, and percent. Supported units align with the typechecker quantity parser: amount supports `mmol` and `mol`; mass supports `mg`, `g`, and `kg`; volume supports `mL`, `ml`, `L`, and `l`; temperature supports `C`, `°C`, `℃`, `K`, and `F`; time supports `h`, `hr`, `hrs`, `min`, `mins`, `分钟`, and `小时`; pressure supports `bar`, `atm`, and `psi`; concentration supports `M` and `mM`; equivalent supports `equiv` and `eq`; percent supports the compact `%` suffix and the `percent` word.

Template body can contain Markdown, structured blocks, and nested `:::use` calls. Expanded nodes continue through resolver and typechecker, so objects inside templates still follow ID, reference, and required-field rules.

Layout belongs to the presentation syntax layer. Use `:::col` when a reusable template needs side-by-side presentation, and see [Layout and Presentation Syntax](/en/docs/advanced-language/layout-syntax) for the column grammar and diagnostics.

## Best Practice Example

Use typed parameters when a template creates relationships or quantity-bearing text. Keep object creation outside templates unless every expansion can provide stable IDs.

```md
:::template result-evidence-line
description: result evidence sentence
params:
  - result: ref<result>
  - sample: ref<sample>
  - method: string
  - purity: quantity<percent>

Result @param.result is supported by sample @param.sample using @param.method. Purity is @param.purity.
:::

:::use result-evidence-line
result: @res-main
sample: sample-product
method: HPLC
purity: 98%
:::
```
